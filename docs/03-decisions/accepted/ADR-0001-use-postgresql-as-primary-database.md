# ADR-0001: Use PostgreSQL as Primary Database

**Status:** Accepted  
**Date:** 2026-05-10  
**Deciders:** Cinturon360 engineering team

## Context

Cinturon360 is a multi-tenant SaaS platform with complex relational data needs: org hierarchies, booking workflows, billing ledgers, approval chains, and role/permission matrices. A primary relational database is required. The initial platform design chose PostgreSQL; this ADR codifies that choice and its version pinning policy.

Evidence of the existing choice:
- `Directory.Packages.props` — `Npgsql.EntityFrameworkCore.PostgreSQL` and `EFCore.NamingConventions` are the only ORM packages present.
- `deploy/compose/compose.dev.yaml` — `image: postgres:18-alpine3.22`
- `src/Cinturon360.Data/DependencyInjection/ServiceCollectionExtensions.cs` — `UseNpgsql(...)` with `UseSnakeCaseNamingConvention()`

Alternatives considered at the time: Azure SQL / SQL Server, MySQL, SQLite (testing only). PostgreSQL was selected for its JSON support, row-level security capability, strong open-source ecosystem, and full Npgsql/EF Core 10 compatibility.

## Decision

PostgreSQL is the exclusive primary database for all environments (development, staging, production).

Supporting choices locked by this ADR:
- ORM: EF Core 10 + Npgsql 10.x (snake_case naming via `EFCore.NamingConventions`)
- Migrations: generated by `dotnet ef migrations script --idempotent` and applied via `psql` (not run-on-startup)
- Connection string section key: `ConnectionStrings:Postgres`
- Retry policy: `EnableRetryOnFailure(maxRetryCount: 5)` unconditionally

Version pinning is intentionally left as a separate decision (see ADR-0009).

## Consequences

**Positive**
- Uniform stack across all environments; no multi-dialect ORM quirks.
- `HasQueryFilter`, row-level security, and JSONB are all available if needed.
- Testcontainers.PostgreSql (already in `Directory.Packages.props`) can drive integration tests against a real engine.

**Negative / Trade-offs**
- Azure SQL managed instance is not usable; any future Azure migration must keep an Azure Database for PostgreSQL Flexible Server.
- EF Core in-memory provider (`Microsoft.EntityFrameworkCore.InMemory`, also in `Directory.Packages.props`) gives false coverage — PostgreSQL-specific behaviour (constraints, sequences, JSON operators) is only validated against a real instance.

**Required follow-up**
- Resolve Postgres version inconsistency across `compose.dev.yaml`, `README.md`, and `v5-plan.md` (see ADR-0009).
- Replace EF Core in-memory test usage with Testcontainers before any integration-test suite is written.
