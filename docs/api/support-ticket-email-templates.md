# Support Ticket Email Templates

This document describes how support-ticket update emails are rendered and sent.

## Overview

Support-ticket emails are sent through the MailerSend-backed `IEmailService`, but the email body is rendered from template content stored in the database.

Templates are managed by the vendor through the API and selected per organisation by template code.

A ticket email is sent only when all of the following are true:

- The ticket owner enabled `Email me updates` on that ticket
- The update is public
- The ticket owner has a usable email address on file
- The public update was not created by the ticket owner themselves

## What counts as a public update

The current implementation sends email notifications for these public ticket events:

- Public comment added to the ticket
- Ticket escalated
- Ticket de-escalated
- Ticket closed
- Public attachment uploaded

Private comments and private attachments do not send email notifications.

## Template storage model

Templates are stored in the `ticket_email_templates` table.

Each row contains:

- `Code`: logical template code, for example `template_support_ticket_helloworld_travel`
- `LanguageCode`: language/culture variant, for example `en-US` or `fr-FR`
- `HtmlBody`: HTML email template
- `PlainTextBody`: plain text email template
- `Description`: optional admin note
- `IsActive`: whether the template can be used

A single logical template therefore has one row per language.

## Naming convention

The recommended source-file naming convention is:

- `template_support_ticket_helloworld_travel_en-US.html`
- `template_support_ticket_helloworld_travel_fr-FR.html`

When loading templates through the vendor API:

- `Code` should be `template_support_ticket_helloworld_travel`
- `LanguageCode` should be `en-US` or `fr-FR`
- `HtmlBody` should contain the file contents
- `PlainTextBody` should contain the text variant for the same template/language

The database does not store the `.html` filename itself. It stores the logical code plus language.

## Organisation selection

Each organisation has a `SupportTicketEmailTemplateCode` field.

If this field is set, ticket emails for users in that organisation will try to use that template code.

If this field is empty, the system falls back to the default code:

- `template_support_ticket_default`

## Language selection and fallback

The email template language is resolved from the ticket owner's `User.LanguageCode`.

Resolution order:

1. Organisation template code + exact user language
2. Organisation template code + `en-US`
3. Default template code + exact user language
4. Default template code + `en-US`
5. Built-in fallback HTML/text generated by the application

Examples:

- User language `fr-FR`: use `fr-FR` if present, otherwise `en-US`
- User language `de-DE`: if no `de-DE` variant exists, use `en-US`
- User language `en`: normalized to `en-US`

## Subject lines

The email subject is system-generated and localized separately from the stored body templates.

Current subject behavior:

- `en-US`: `Support ticket update {ticket_id}: {ticket_subject}`
- `fr-FR`: `Mise a jour du ticket {ticket_id}: {ticket_subject}`
- Any unsupported language falls back to the `en-US` subject

This means body templates come from the database, while subject selection remains controlled by the application.

## Placeholder syntax

Templates use double-brace placeholders:

- `{{ticket_id}}`
- `{{ticket_subject}}`
- `{{ticket_status}}`

Unknown placeholders are replaced with an empty string.

## Available placeholders

The current implementation supports these placeholders:

- `{{ticket_id}}`
- `{{ticket_subject}}`
- `{{ticket_status}}`
- `{{ticket_priority}}`
- `{{ticket_queue}}`
- `{{ticket_category}}`
- `{{ticket_created_at_utc}}`
- `{{ticket_updated_at_utc}}`
- `{{ticket_url}}`
- `{{update_type}}`
- `{{update_body}}`
- `{{updated_by_name}}`
- `{{updated_at_utc}}`
- `{{user_full_name}}`
- `{{user_email}}`
- `{{org_name}}`
- `{{support_team_name}}`

## Example HTML template

```html
<html>
  <body>
    <h2>Support ticket update</h2>
    <p>Hello {{user_full_name}},</p>
    <p>Your ticket <strong>{{ticket_id}}</strong> has a new public update.</p>
    <p><strong>Subject:</strong> {{ticket_subject}}</p>
    <p><strong>Update type:</strong> {{update_type}}</p>
    <p><strong>Updated by:</strong> {{updated_by_name}}</p>
    <p><strong>Message:</strong></p>
    <div>{{update_body}}</div>
    <p><a href="{{ticket_url}}">Open ticket</a></p>
  </body>
</html>
```

## Vendor API

These endpoints exist for template management:

- `GET /api/v1/system/ticket-email-templates`
- `GET /api/v1/system/ticket-email-templates/{templateId}`
- `PUT /api/v1/system/ticket-email-templates`
- `DELETE /api/v1/system/ticket-email-templates/{templateId}`

The write endpoint expects:

```json
{
  "code": "template_support_ticket_helloworld_travel",
  "languageCode": "en-US",
  "htmlBody": "<html>...</html>",
  "plainTextBody": "Plain text version",
  "description": "Travel-branded support template",
  "isActive": true
}
```

These endpoints are intended for vendor/global-admin use only.

## Vendor UI

The vendor portal now exposes a read-only management page at `/vendor/ticket-email-templates`.

- It lists stored templates
- It renders the stored HTML for preview
- It shows the plain-text variant
- It supports delete only

Create and update remain API-only.

## Organisation API field

Organisation updates now accept:

- `SupportTicketEmailTemplateCode`

This allows a vendor or authorised organisation admin flow to point the organisation at a vendor-provided template code.

## Ticket UI behavior

The user can control email updates in two places:

- When raising a new ticket, using the `Email me updates` checkbox
- On the ticket detail page, using the `Email me public updates` preference control

The default is off.
